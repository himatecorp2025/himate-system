# HIMATE START-24 — Final Security Acceptance

## Purpose

START-24 is the final security acceptance gate over the already closed START-23.12 production release. It validates the existing authentication, authorization, tenant-isolation, browser, abuse-protection, service-identity, webhook, secret-management and deployment boundaries without changing HIMATE business workflows or expanding the product security feature set.

The accepted production release identity remains `0.8.33-start-23.12`; START-24 is an acceptance/hardening gate, not a new product-feature release.

## Scope and invariants

### START-24.1 — Authentication, sessions and MFA

- Existing administrator and sensitive Partner Portal MFA behavior remains unchanged.
- Login throttling remains active until MFA succeeds; an attacker cannot clear the password-failure throttle merely by reaching the MFA challenge.
- Failed MFA verification contributes to authentication throttling and successful MFA clears it.
- MFA challenges retain the existing 10-minute expiry and five-attempt limit.
- Admin and Partner Portal session cookies remain HttpOnly + SameSite=Strict and use the existing Secure production policy.
- Authentication-state changes rotate session versions. Partner email, role and active-state changes invalidate existing Partner Portal sessions.

### START-24.2 — RBAC and tenant isolation

- Public clients cannot inject HIMATE authority headers; Gateway strips them before reconstructing authority from authenticated identities.
- Partner Portal tenant authority comes from the signed partner session, never from caller-supplied partner IDs.
- Partner user administration and user-module assignments are constrained by `partner_id` at the database boundary.
- Runtime module execution requires both active organization entitlement and effective user assignment.
- Tenant Finance reads and mutations remain partner-scoped and tenant idempotency keys remain tenant-scoped.
- Notification visibility remains intersected with tenant, target user, permission and module scope.
- Historical executable cross-tenant regression proofs remain mandatory.

### START-24.3 — API, input and browser security

- Shared JSON decoding remains bounded to 1 MiB, rejects unknown fields and rejects trailing JSON values.
- Browser mutations retain exact-origin + Fetch Metadata protection.
- Public-origin construction does not trust `X-Forwarded-Host`.
- CMS/navigation URL policy rejects unsafe schemes such as `javascript:` and `data:`.
- Dynamic server-rendered CMS text and URL attributes remain HTML-escaped.
- Existing CSP, HSTS-on-HTTPS, frame, MIME, referrer and permissions headers remain active.

### START-24.4 — Abuse, rate-limit and resource bounds

- Existing five-failure / fifteen-minute authentication lockout semantics remain unchanged.
- Authentication throttle state is bounded and pruned so attacker-controlled source keys cannot grow process memory without limit.
- HTTP read-header/read/write/idle timeouts remain active.
- Stripe webhook, CMS media and storage object request bodies remain hard-bounded.
- This phase does not replace edge/provider DDoS mitigation; it validates the application-layer resource bounds behind that edge.

### START-24.5 — Secrets, service identity and webhooks

- Platform secrets remain encrypted at rest and write-only through the administration surface.
- Source-controlled Render configuration does not contain literal provider/database/SMTP credentials.
- Automation Finance identity is generated by Render and shared through the declared service reference.
- Private `/internal/v1/` requests retain timestamped HMAC service identity and authority-header integrity.
- Automation event identity remains body-bound and time-bounded.
- Stripe webhooks retain signature validation, time tolerance, event/payload replay conflict protection, processed-event idempotency and payment identity/amount reconciliation.

### START-24.6 — Supply chain and deployment

- Go production/CI toolchain is pinned to Go 1.27.1.
- pgx baseline is v5.11.0.
- Every Go service Docker builder uses `golang:1.27.1-bookworm`; no Go 1.23 builder remains.
- Render production auto-deploy stays disabled and Vercel deployment remains disabled for the repository.
- Production services keep one synchronized START-23.12 release identity.

### START-24.7 — Cross-phase closure

The closure gate reruns START-24.1 through START-24.6 together, requires both Fast CI and Full CI integration, retains the complete START-23.12 production-acceptance regression, runs the dedicated START-24 runtime security smoke and retains Go race detection.

## Dedicated runtime proof

`scripts/smoke_start_24.sh` proves at runtime:

- security response headers and API no-store policy;
- cross-site browser mutation rejection;
- forged session rejection;
- authentication throttling and client isolation;
- bounded oversized JSON handling;
- unsigned Stripe webhook rejection;
- service health after abuse-path tests.

## Explicitly deferred product work

START-24 does **not** implement trusted-device behavior or change how often MFA is requested. The future product roadmap reserves:

- Module 39: requirements/intake module;
- Module 40: optional two-factor-authentication module, including a later trusted-device / remembered-device design.

Those changes require their own product/security design and must not be folded into START-24 acceptance.

## Terminal acceptance rule

START-24 closes only when the same PR/head passes:

- Fast CI: preflight, Go, Flutter and current Compose regression;
- Full HIMATE CI: Go tidy/vet/test/race/build, Flutter analyze/browser/release build, complete historical Compose regression, all START-24 audit contracts and the START-24 runtime security smoke;
- the target PR remains mergeable into `develop`.

Only after those gates are green may START-24 be merged and the roadmap move to the manual Central Admin + Test Partner UI/UX audit.
